# 六育学生评价系统减负与成长报告改造规格

版本：1.0；日期：2026-10-27。由当前对话、需求材料、现有实现和上一轮评审草案综合形成。本规格发布到本仓库的本地 Markdown 问题跟踪器。

## Problem Statement

学校希望“减少老师操作、简化积分流程、重新设计学生端、自动生成学期报告”。这是用户在本次讨论中明确确认的四个目标。

当前学生领到奖励卡后，扫码只产生待审申请，老师还要逐张选择子类、确认加分。积分错误需要管理员处理。日常奖励的简单操作因而分散成多次线上操作，增加教师负担，也延迟学生获得成长反馈。

现有学生界面沿用管理工作台的布局，成长记录分散在积分、荣誉、故事与报告页面，缺少适合小学生的清晰入口、角色元素与及时反馈。

期末评价仍主要依赖管理员导入六育终测分，再叠加过程与荣誉得分。若取消终测导入却保持原算法，系统无法按新要求自动形成评价，还可能重复计算同一证据。现有报告虽能保存快照与打印，但教师确认、真实家长输入、细粒度成绩授权和“管理员只看完成状态”的流程尚未完整建立。

成功应表现为：教师不再逐卡审核；学生扫卡后及时看到正确的 +1；教师能自行在授权范围纠错；期末数据自动汇总，教师只补充必要评价并确认寄语；管理员依准备状态发布；学生和家长获得易理解、可打印、版本稳定的成长报告。

## Solution

在现有系统上改造积分、评价、报告与学生体验，复用已经具备的认证、学期配置、自动配卡、二维码打印、材料版本与报告快照能力。

日常卡只保留德育 D 和智育 Z，生成时确定奖励方向与完整子类。学生身份明确后，扫码以一次事务完成兑换与 +1，不再进入教师逐张审核。教师负责授权班级的例外处理与无卡直评，系统保留更正历史。

荣誉由教师审核时确定体育 T、美育 M 或劳育 L 归属，并按已批准规则计分；成长故事支持输入、粘贴、规则建议分与教师终审；任课教师仅能管理自己任教班级、对应学科的数据。六育评价从有效来源按学期规则自动生成，原始事实、维度结果和报告展示等级保持区分。

学生使用独立的成长界面，查看个人六维成长、兑换反馈、成长足迹、荣誉、故事和学期报告。现有“成长森林”草图是讨论参考，具体风格与游戏成长等级仍待确认。教师与管理员界面保持简洁，移除已不适用的操作。

报告自动汇总六育结果、成长证据、学科、行为、健康、故事及寄语；班主任审核最终内容后进入可发布状态。管理员只查看完成状态并批量发布。电子版和 A4 打印版使用相同发布快照，后续修改通过新版本体现。

分期保持需求材料的优先级：P0 完成积分卡主链路；P1 完成评价、报告及学生端；P2 预留统一登录和设备扩展。若公共扫码设备是一期开卡的必要条件，其身份识别与会话能力须提前纳入 P0。各阶段采用哪些学校规则，受本规格列明的决策依赖约束。

## User Stories

1. 作为一名教师，我希望不再逐张审核学生领取的日常积分卡，以便把时间用于教学和实际评价。
2. 作为一名教师，我希望日常卡只区分德育和智育，以便快速理解并发放合适的奖励。
3. 作为一名教师，我希望卡片在生成时已经确定完整分类，以便发卡后无需再次在线选择子类。
4. 作为一名教师，我希望卡面能清楚表达奖励事由，以便把正确的卡发给学生。
5. 作为一名管理员，我希望沿用可配置的学科配卡能力，以便集中维护教师份额和制卡规则。
6. 作为一名管理员，我希望方向及子类的生成数量符合配置且总量守恒，以便核对打印与分发数量。
7. 作为一名管理员，我希望重复生成和重印使用同一批卡，以便避免无意增加可兑换奖励。
8. 作为一名学生，我希望扫有效卡后立即获得 1 分，以便及时看到自己的努力得到回应。
9. 作为一名学生，我希望成功页面显示奖励方向、具体分类和加分结果，以便知道这次表扬来自什么表现。
10. 作为一名学生，我希望成功反馈有简短动画且可以跳过，以便获得鼓励并继续自己的活动。
11. 作为一名学生，我希望未登录扫码后可以恢复领取意图，以便完成身份验证后继续兑换。
12. 作为一名学生，我希望重复扫码清楚提示已领取且不重复加分，以便正确理解自己的积分。
13. 作为一名学生，我希望遇到超时可以安全重试，以便不会因不确定的响应而多领或漏领奖励。
14. 作为一名学生，我希望卡片过期、作废、未生效或不可用时得到明确反馈，以便知道下一步该怎样处理。
15. 作为一名教师，我希望查看自己获授权班级的积分历史，以便发现并处理误发或误扫。
16. 作为一名教师，我希望能够撤销错误奖励，以便自行纠正错误而无需管理员介入。
17. 作为一名教师，我希望在允许范围内修正分值或分类并填写原因，以便让成长记录反映真实情况。
18. 作为一名教师，我希望看见积分更正的原记录、原因和处理历史，以便解释学生的积分变化。
19. 作为一名教师，我希望多人或重复操作同一笔纠错不会重复扣分，以便保持账目准确。
20. 作为一名教师，我希望卡用完、遗失或临时需要表扬时仍能无卡直评，以便不打断教学。
21. 作为一名教师，我希望能对授权学生批量直评且提交重试不重复发分，以便高效完成课堂表扬。
22. 作为一名管理员，我希望退出逐笔积分审核与取消操作，以便专注于配置和学校层面的完成情况。
23. 作为一名学生，我希望上传奖状并填写比赛级别、获奖等次和日期，以便提交自己的荣誉证据。
24. 作为一名审核教师，我希望通过荣誉时选择体育、美育或劳育归属，以便把奖励计入正确维度。
25. 作为一名审核教师，我希望系统按有效规则计算荣誉分，以便减少手工计算和口径差异。
26. 作为一名学生，我希望荣誉被驳回时看到原因，以便针对问题修改并重新提交。
27. 作为一名审核教师，我希望重提材料、复核和认定保留版本，以便核查每次判断的依据。
28. 作为一名审核教师，我希望同一荣誉不会因重复申报或审核重试而多次计分，以便保持公平与准确。
29. 作为一名审核教师，我希望荣誉撤销或更正时关联奖励同步调整，以便认证状态与积分一致。
30. 作为一名学生，我希望直接输入或粘贴成长故事并保存草稿，以便用方便的方式记录生活。
31. 作为一名学生，我希望明确知道故事处于草稿、已提交还是已终审状态，以便理解哪些内容仍可修改。
32. 作为一名评阅教师，我希望系统提供可解释的故事建议分，以便加快评阅而保留最终判断权。
33. 作为一名评阅教师，我希望能调整建议分并确认正式分，以便使评价符合真实内容和学校要求。
34. 作为一名学生，我希望学期故事评价考虑规定期间的有效作品，以便整学期的记录得到合理呈现。
35. 作为一名任课教师，我希望导入自己任教班级、对应学科的成绩，以便减少重复录入。
36. 作为一名任课教师，我希望导入前看到字段映射、有效行、错误和更正差异，以便确认数据再写入。
37. 作为一名任课教师，我希望预览和提交都校验授权，以便不能通过更改请求或旧入口写入其他学科。
38. 作为一名任课教师，我希望只能读取自己有权限管理的成绩，以便履职所需数据范围清楚。
39. 作为一名教师，我希望空白、零分、等级、星级、缺考、免测和不适用被正确区分，以便避免误评学生。
40. 作为一名管理员，我希望取消手工导入六育终测成绩，以便系统直接从有效来源形成评价。
41. 作为一名管理员，我希望维护版本化的学期、指标、学科策略和评分规则，以便学校口径一致且可追溯。
42. 作为一名班主任，我希望看见六育结果的来源和缺项，以便补齐真正缺少的评价。
43. 作为一名学生，我希望同一笔积分或荣誉不会被重复计入评价，以便得到准确的成长结果。
44. 作为一名学生，我希望没有获奖时仍能通过常规学期评价完成报告，以便不因缺少竞赛经历而被误判数据不全。
45. 作为一名教师，我希望系统明确区分未采集和已确认的零记录，以便不把缺项当作零分。
46. 作为一名班主任，我希望学校明确授予汇总证据和报告职责，以便完成学期总评并保持权限边界。
47. 作为一名班主任，我希望自动汇总积分、荣誉、故事、学科及其他适用指标，以便不再为报告重复整理数据。
48. 作为一名班主任，我希望系统基于已确认的事实生成 AI 寄语初稿，以便减少从空白撰写的工作。
49. 作为一名班主任，我希望看到寄语引用的证据和不足提示，以便核实内容而不采纳编造判断。
50. 作为一名班主任，我希望能修改、确认并保留寄语版本，以便对最终文案负责。
51. 作为一名班主任，我希望生成失败时仍能保存和手写寄语，以便不丢失已完成的工作。
52. 作为一名管理员，我希望只查看报告完成数量、缺项和可发布状态，以便完成发布管理而不读取个人报告正文。
53. 作为一名管理员，我希望批量发布满足门槛的报告并看到受阻原因，以便集中处理期末发布。
54. 作为一名班主任，我希望确认后数据发生变化时报告重新进入待确认状态，以便不把旧确认误用于新数据。
55. 作为一名学生，我希望发布后的报告保持稳定，以便电子阅读和纸质打印有一致依据。
56. 作为一名学生，我希望源数据更正通过明确的新发布版本体现，以便知道报告何时改变。
57. 作为一名学生，我希望报告以等级和成长事实为主并保留六育雷达图，以便读懂自己的学期表现。
58. 作为一名学生，我希望报告按成长总览、证据、学科、故事和寄语分区展示，以便像翻阅成长手记一样阅读。
59. 作为一名班主任，我希望电子版与 A4 打印版读取同一发布内容，以便减少导出和核对工作。
60. 作为一名班主任，我希望打印时中文、星级、长寄语、表格和签名区域清楚可读，以便直接发放纸质报告。
61. 作为一名家长，我希望通过学校确认的身份渠道填写寄语，以便真实表达对孩子的鼓励。
62. 作为一名家长，我希望寄语记录填写来源、时间和版本，以便知道内容如何进入报告或反馈记录。
63. 作为一名家长，我希望发布后补填寄语不会静默改变旧报告，以便保留已经阅读或打印的内容。
64. 作为一名学生，我希望使用适合小学生的彩色界面和角色元素，以便愿意主动查看成长记录。
65. 作为一名学生，我希望首页突出扫码与个人成长，以便快速找到最常用的功能。
66. 作为一名学生，我希望在统一成长足迹中查看积分、荣誉、故事和评价，以便看见它们之间的联系。
67. 作为一名学生，我希望游戏成长反馈与学校评价等级清楚区分，以便不把动画等级误认为正式成绩。
68. 作为一名管理员，我希望后续可以按学期或活动更换主题，以便保持新鲜感而不改动业务数据。
69. 作为一名教师或管理员，我希望工作台保持简洁、信息清楚，以便快速完成自己的业务。
70. 作为一名学生或教师，我希望系统预留钉钉身份关联，以便条件具备后统一登录并进入正确界面。
71. 作为一名使用公共扫码设备的学生，我希望设备先识别我的身份再兑换奖励，以便积分记到自己名下。
72. 作为一名使用公共扫码设备的学生，我希望完成后及时清除个人会话与展示，以便下一位同学不会沿用我的身份。
73. 作为一名学校负责人，我希望根据实际设备确定手机专项优化范围，以便把开发投入用在真实使用场景。
74. 作为一名管理员，我希望兼容学校学籍表并预览新增、更新和冲突，以便减少人工整理且不误覆盖账号权限。
75. 作为一名受权体测人员，我希望按样例导入测量值、单位和缺测状态，以便报告展示可信的健康资料。
76. 作为一名学校负责人，我希望先盘点旧卡、历史分和报告并明确试点切换方式，以便上线时不漏账或重复奖励。
77. 作为一名学校负责人，我希望回退新流程时仍保留已发生的积分和发布版本，以便异常处理不抹掉学生的真实记录。
78. 作为一名验收人员，我希望用隔离环境中的真实三角色流程及可核对结果验收，以便确认用户可见行为而不是只看到演示动画。

## Implementation Decisions

以下分为需求约束、现有实现约束和本规格采用的工程方向。没有用户答案的学校规则列入 Further Notes，不作为已达成的决定；先前草图中的颜色、分值与等级也不因此转为正式口径。

1. **技术与模块边界。** 在现有 React/Vite/Ant Design、Express、MySQL 架构上改造；覆盖制卡与兑换、积分纠错、荣誉、故事、任教授权及导入、评价计算、报告、学生布局与主题模块。保留现有认证、学期、二维码受控打印、材料版本及报告快照能力；具体内部组织由实施计划确定。
2. **统一领域语言。** 日常“卡型”只有 D/Z；“六育维度”仍为 D/Z/T/M/L/G。来源事实、原始分、维度结果、正式展示等级和游戏成长等级分别表达。继续使用现有六维编码，外部表头和报告建议中的其他编码通过显式映射处理。
3. **制卡定类。** 卡片在生成时必须确定学校、学期、责任教师、D/Z 方向、有效叶子指标、完整分类路径与版本、固定 +1、批次和有效期。策略应能配置方向及子类份额，方向/子类整数数量守恒；子类实际分布、现有月度主教学科配额如何沿用仍依赖对应决策。
4. **卡片凭证与重印。** 复用高熵凭证、哈希校验和受控打印；生成重试与重印不增加可兑换资产。指标修改不覆盖卡片生成快照，旧版卡如何继续兑换由切换规则确定。不得把无子类的旧卡随机绑定分类。
5. **即时兑换接口契约。** 输入为已识别学生身份、卡片凭证及稳定请求键；成功输出兑换标识、积分流水标识、方向/分类、实际入账 +1 和结果时间。同一请求重放返回同一结果；已使用、失效或越权返回明确业务状态，不产生第二次奖励，也不向其他学生泄露领取人。
6. **事务与唯一性。** 验证身份与可用性、锁定卡片、写兑换事实、写唯一原始奖励、标记已使用及审计，在同一事务完成。新卡不经过人工待审；历史待审保持原事实并按已确认切换策略处理，不能伪造人工审核人来满足旧表约束。现有状态、检查约束与唯一关系须同步迁移。
7. **身份与设备。** 兑换必须绑定明确学生身份。个人登录和公共设备属于不同会话场景；奖励卡本身不作为学生身份。公共设备若启用，需学校绑定、限定兑换能力、短会话、学生切换与结果清屏。实际凭证、设备与一期范围是前置决策。
8. **纠错账本。** 复用追加式积分账本。撤销追加冲销；改分类/改允许分值以冲销当前有效项和写替代项表示，记录原奖励、更正链、操作教师、原因、时间与稳定幂等标识。更正同一奖励应串行化，同一有效项最多冲销一次；替代项不能占用原卡片唯一入账身份。更正后卡仍已使用。
9. **分值与直评。** 现有仅允许 ±1 的约束及积分来源不足以承接改分和荣誉，需要明确扩展；扩展不等于向教师开放任意分值、负分或维度。无卡直评继续支持授权学生批量奖励与稳定重试；允许方向、分值和关闭学期的处理以学校决策为准。
10. **荣誉事实与奖励。** 保留申报、材料版本、驳回理由和重提流程，审核确认 T/M/L 归属、规则版本与正式奖励并保持事务一致。使用稳定的赛事届次/奖项依据去重；同一材料和审核事件不重复记账。认定撤销或更正同步纠正奖励。旧固定 1—9 分是现状，新的级别/等次规则不得直接假定。
11. **单一计分来源。** 推荐复用积分账本承接已认定荣誉奖励，荣誉主记录保留事实和认定依据；汇总只统计一遍。故事终审百分分是评价事实，不直接等于奖励积分。不得再无条件叠加已经参与六维计算的同一过程或荣誉分。
12. **故事评价。** 复用草稿、提交、材料版本及教师终审。建议分明确标为规则建议，保存依据与版本；长度不能证明真实成长。学期 G 使用已批准月份与聚合规则的有效终审记录，不默认以最后一篇覆盖整学期。读、听、讲指标与原创故事并存。
13. **精确任教授权。** 引入学校、学期、教师、班级与学科的明确关系；不能由独立的班级列表与学科列表相乘推断。班主任是单独授予的班级职责。读取、导入、审核、纠错、报告和附件访问都执行服务端资源范围检查；管理员主角色不默认继承教师业务能力。
14. **成绩导入契约。** 输入包含目标学期/授权学科、映射版本与原始行；预览返回有效项、错误与更正差异。提交重新校验当前授权、学生、学科、数值/等级和状态，不信任客户端返回的有效名单。单项旧入口和批量入口执行相同范围要求。更正保留批次、责任人及有效版本。
15. **来源值类型。** 保留原值并明确区分数值、等级、星级、文本、缺失、缺考、免测与不适用。稳定学号优先于姓名匹配；未经学校规则，不把三星、A 与百分分互相转换。有效 0 与未采集分别处理。
16. **自动六维核算。** 停止新流程管理员六育终测导入，以有效来源及版本化规则计算各维度结果、状态、分解与证据引用。规则支持适用年级、来源选择、归一化、权重、目标线、封顶、等级与缺项策略；实际参数及是否保留综合总分仍是决策依赖。没有荣誉不自动视为数据缺失，常规评价完成要求与奖励次数分开定义。
17. **指标模型。** 以学校和版本范围内的指标字典与类型化结果承接报告字段，配置年级适用、单位、允许值、显示和必填策略，关联有效来源而不为报告重复记账。不能把建议稿全部 74 项固定为所有学生必填，也不照抄未适配现有主键、学校边界的示例 SQL。
18. **管理员状态接口。** 发布准备状态与个人报告内容分离。管理员仅获得完成数量、缺项代码、允许的身份/班级标识及发布结果；具体状态清单身份字段待确认。详情、打印、综合评价、材料、审计摘要和发布响应都不得绕回个人成绩、寄语、健康或报告快照。
19. **报告生命周期。** 复用现有报告主实体，形成草稿、待教师确认、可发布、已发布和已替代状态。可发布状态绑定来源数据、评分规则、模板与教师确认版本；确认后数据变化使草稿重新待确认。家长寄语是否构成发布门槛仍待学校决定。
20. **发布契约与快照。** 管理员提交符合准备状态的报告及预期版本；每份报告在事务中重新校验并冻结身份/班级、学期、有效证据、结果/等级、指标、教师寄语、家长内容及来源、规则和模板版本。新版本成功后才替代旧版。批量可部分成功，但单份失败不能破坏旧版；并发和重试不能制造重复有效版本。
21. **发布后的读取。** 学生及其他获授权人员按报告版本读取和打印，正文完全来自该发布快照；实时姓名/班级、源成绩或反馈修改不能静默改变旧版。独立标明的本次打印时间不属于原报告正文。历史版本按授权和替代状态展示。
22. **寄语生成与人工确认。** 合并表达教师寄语/学期总述，使用已确认评价事实、故事和审核证据生成初稿，提供证据及不足提示，班主任编辑确认最终版本。保存生成方式、生成规则或模型版本及修订；失败不覆盖已确认文本。真实 AI 与模板兜底必须区分，只有模板不能算完成 AI 功能。模型渠道、实际启用及一期分期以学校决策为准。
23. **生成数据范围。** 不默认发送姓名、学号、健康、家庭等信息到生成服务；无依据不编造奖项、性格、名次、诊断或进步趋势。健康值只在获授权的报告区域展示，不能直接作为奖惩积分。模型输入/输出来自所选证据，生成失败允许明确重试或人工起草。
24. **家长反馈。** 家长填写必须记录身份依据、来源、时间和版本；学生代录若被允许须明确标注。受限、可撤销的监护人填写入口是待确认候选，不能把已有文本字段当成实名家长流程。发布前纳入正文和发布后独立反馈分别处理；发布后改正文需显式新报告版本。
25. **报告与打印。** 电子报告按成长总览、证据、行为、学科、健康、故事、教师/家长寄语及署名分区，正式等级优先并保留雷达图。A4 与电子版共用发布数据，打印取消动态效果并保证中文、星级、长文本和分页可读。页数、单双面、印章和具体字段根据学校原样例确认。
26. **学生体验。** 学生使用独立布局和统一成长足迹；兑换成功反馈只能由实际成功结果触发，重复/失败不显示新奖励动画。动画短、可跳过并支持减少动态偏好。主题以配色、背景、角色和图标配置切换，不影响积分、规则或报告版本。首版一套主题及成长森林方向均仍待视觉确认。
27. **学籍与体测导入。** 学籍为独立基础资料权限，按学校/稳定学号、样例映射与版本区分新增、更新、重复和冲突，确认后留批次记录；不覆盖密码、角色、成绩或发布快照。体测另行授权，明确测量时间、单位、原值及缺测/免测；未知格式和异常值进入核实，不自动推断健康状况。
28. **统一登录预留。** 保留外部身份到校内用户、学校、角色和职责的映射能力，不由客户端自行选择身份权限；实际钉钉绑定、解绑和接入条件待确认。设备决定手机专项优化范围，避免在硬件未定时承诺专项覆盖。
29. **迁移与旧入口。** 按确认的学校/学期切换方案盘点旧卡、待审、已记账和已发布内容。已用卡不重发奖励；历史算法与报告保留原版本；待审和缺分类卡不能擅自转换。新流程停用旧逐卡审核、管理员冲销及六育终测写入能力，服务端拒绝绕行。二维码兑换入口变更须考虑已印刷链接。
30. **回退边界。** 回退新入口与启用配置时保留已发生的积分、更正和发布版本，使用受控更正恢复一致性，不能覆盖数据库抹掉上线后的有效记录。操作手册、测试夹具和全系统演示应同步新行为，旧历史资料保留其时间背景。

## Testing Decisions

### 已确认的验收边界

用户于 2026-10-27 明确确认：**以“三角色真实浏览器端到端流程”为主要验收边界，沿用现有独立测试库；仅对并发兑换、越权请求和发布事务补充真实 API／数据库集成测试。**

1. 优先扩展现有全系统浏览器演示/验收入口，不为每个内部模块新建一套测试通道。主要操作从真实 UI 发生；可用只读 API 或数据库对账核验结果，不用直接写库替代用户操作。
2. 良好测试断言可观察的结果：是否只加一次分、是否能越权、报告是否完整且保持版本稳定、用户看见什么状态。避免断言内部调用顺序、SQL 字符串、私有函数名或组件实现。
3. 每次完整验收使用隔离数据库、虚构多学生与多角色、专用本机服务及浏览器会话，避免写入现有业务库。错误情形保留失败结果和证据，不能跳过后报告通过。
4. 浏览器主链路覆盖配置与制卡、兑换/重复反馈、教师直评/纠错、荣誉退回与重提、故事评阅、授权导入、自动六维、寄语确认、状态发布、本人查看和 A4 打印。学生主题与成长记录在该主链路中检验。
5. 班主任以明确职责的教师身份覆盖；家长渠道与公共设备确认纳入范围后，从对应真实入口补入同一业务验收体系，而不是绕过身份只测试输入框。模型服务若不可用必须体现失败/延期状态，不能用模拟文本宣布 AI 功能通过。

### 集成测试补充范围

| 对外模块 | 必须验证的行为 | 为什么需要补充 |
| --- | --- | --- |
| 兑换与奖励 | 同请求重放、同卡换请求、多学生并发、提交后响应超时、重复/失效卡只产生一次原始奖励 | 浏览器顺序操作不足以稳定覆盖竞争与提交边界 |
| 纠错与正式认定 | 并发更正和重复提交不多扣/多加；荣誉通过、更正、撤销与奖励一致 | 属于同一奖励事务一致性边界，不以内部方法测试替代 |
| 身份和数据授权 | 跨校/跨学生/跨班/跨学科、未经授予的班主任职责、管理员经详情/打印/审计/旧入口访问均拒绝；提交改体不能绕过预览 | 页面菜单不能证明服务端安全边界 |
| 报告准备与发布 | 确认后数据变化阻止旧确认发布、并发幂等、单份失败回滚、整批部分成功及旧版继续可读 | 验证版本绑定与每份报告的原子性 |

集成测试使用真实应用 API 与真实 MySQL 状态，必要的故障注入只用于触发事务失败条件；最终仍以对外结果与持久化一致性断言。模型等外部服务的受控失败属于端到端场景输入，不作为重新拆分内部测试边界的理由。

### 关键验收结果

1. D/Z 卡数量及叶子归类正确，扫码后教师待审数量不增长；无子类或不允许方向不误发日常卡。
2. 正常兑换 +1；同卡并发、断网重试、重复扫码仍只有一笔原始奖励。错误反馈不误报成功，其他学生看不到领取人。
3. 撤销、改分类、允许改分保留原事实；重复/并发纠错不多扣，原卡不恢复可用。直评重试不重复记分。
4. 荣誉 T/M/L 归类、规则计分、理由驳回与重提正确；认定与奖励一致并且只计算一次。
5. 故事建议与正式分区分；按已确认期间聚合而非默认取最后一篇。证据不足不凭篇幅作事实判断。
6. 教师仅教甲班语文、乙班数学时，不能读写甲班数学；旧入口和伪造提交同样被阻止。
7. 空白、0、等级、星级、缺考、免测、不适用正确区分；没有获奖但常规评价齐备不因此受阻。
8. 停止新流程六育终测导入后，仍可从规则认可的来源形成六维，积分/荣誉不重复加权；未配置规则不能伪造最终等级。
9. 寄语基于可核实证据，教师可以修改确认；生成失败不覆盖人工文本；模板兜底不标为真实 AI 成果。
10. 管理员的状态与发布响应不泄露个人分数、故事、寄语、健康或报告正文，替代访问路径也不能绕过。
11. 确认后的数据改变使准备状态失效；失败发布不破坏旧版；发布后改姓名、班级、成绩和家长反馈不静默改变原正文。
12. 电子报告和 A4 使用同一发布版本；用真实最长字段检验中文/星级、跨页表格、长寄语、署名与签章位置。原校样例未确认前不宣称版式验收完成。
13. 学生独立布局、成长记录与主题切换正常；游戏成长等级不冒充正式评价，切主题不改业务数据。
14. 公共设备若启用，验证身份切换、超时、限权与清屏；学籍/体测导入按批准样例和受权角色验证，不覆盖账号权限或已发布内容。
15. 旧卡与旧报告按选择的切换策略保持可解释、可对账；回退不抹掉新流程的有效记账。

### 已有测试先例及边界

- 现有全系统自动演示已具备独立数据库、三角色 UI 操作、真实二维码/打印、虚构多学生与只读对账，可作为主要入口扩展。
- 已有真实卡片事务集成测试覆盖同卡并发、请求重放、期限、跨校与旧卡拒绝，可沿用其环境和外部断言方式，改写原“扫码先待审”的预期。
- 已有权限回归、成绩导入、报告重发及快照核对案例可作为行为场景参考，不继续依赖已退役审核和管理员终测作为新流程成功路径。
- 现有某批量写入压测重复使用同一个学生身份，不能作为多学生数据隔离、真实学校容量或新性能指标的证据。性能目标需结合试点规模确定，本规格不继承未经确认的耗时承诺。
- 本轮只是规格编制，不代表以上新业务测试已实施或通过。
