# 六育学生评价系统项目执行与技术实现计划书 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在保留历史数据与权限边界的前提下，交付教师减负、扫码即时入账、适龄学生端及自动成长报告，并分别验证P0和P1试点。

**Architecture:** 沿用模块化单体和同一MySQL事务边界，不拆微服务。以实时授权、奖励根及追加账本、学生学期来源版本、已确认报告快照连接各模块；外部模型和设备通过受限适配层接入。

**Tech Stack:** 现有React 18、Vite、Ant Design、Express 5、mysql2/MySQL、JWT、浏览器打印和既有Playwright演示运行器；沿用锁文件，不因本计划升级依赖。

**Spec:** [六育系统改造规格](../../wayfinder/system-renovation/spec.md)；[20票审核报告](../../../.scratch/system-renovation/audit-2026-10-27.md)；[逐任务执行附录](2026-10-27-system-renovation-execution-tasks.md)。

日期：2026-10-27。状态：**审核后的条件型执行基线建议，尚未改变原开发票或校方业务规则**。本轮完成静态审计与计划，不执行产品代码、DDL、外部调用或上线。

## Global Constraints

- Spec：“日常卡只保留德育 D 和智育 Z”，但六育维度仍为D/Z/T/M/L/G；每卡成功兑换固定+1。
- Spec：“任课教师仅能管理自己任教班级、对应学科的数据”；班主任职责另行授予，管理员只看准备状态。
- Spec：“电子版和 A4 打印版使用相同发布快照，后续修改通过新版本体现。”
- 用户已确认：以“三角色真实浏览器端到端流程”为主要验收边界，沿用独立测试库；仅对并发兑换、越权请求和发布事务补真实API／数据库集成测试。
- 原始值、来源证据、正式评价、展示等级和游戏成长等级分别表达；缺失不补零、无获奖不等于数据不全。
- 不推定80/15/5、新荣誉1—9分、三星=A、全部74项必填或模型/设备已获授权。
- 不清空历史积分、伪造审核人、覆盖已发布正文，不将模板兜底或身份预留当真实AI/SSO验收。
- OCR、Word故事上传、通用卡、排行、商城、抽奖不在本期范围；真实钉钉接入超出“预留”须另定范围。

## Review Focus

1. 同一JWT下职责撤销、账号停用或学生转班：后续请求必须按当前授权拒绝，不能继续使用旧班级快照；归属任教授权票R01。
2. 同卡竞争、提交后丢响应、已纠错后重复扫：仍只有一次原始奖励，回放不产生新加分动画；归属扫码/纠错R03/R04。
3. 导入预览后成绩或权限改变：提交校验服务器批次、输入摘要、授权及预期版本，冲突不静默覆盖；归属导入R08/R17。
4. 寄语生成或教师确认后来源改变，旧AI结果迟到：旧确认不能发布，新结果不能覆盖人工稿；归属草稿/AI/发布R11/R12/R14。
5. 学期月底、旧PENDING卡与新卡混合、DDL中断或回退：按流程版本处理并保持账、卡、报告一致；归属制卡/扫码/20A/20B。

## 第1轮：需求骨架与边界

### 1.1 范围与终态

六条主链路分别为：配置与制卡→学生兑换；教师直评/纠错；荣誉/故事认定；学科/指标/健康采集；自动六维→班主任确认；管理员状态发布→本人阅读/打印/家长反馈。

核心实体是用户/职责、学期、奖励分类与配卡策略、卡片/兑换、奖励根/追加流水、荣誉/故事材料版本、指标字典/结果、学科/健康来源、学生学期状态、评价规则/结果、报告草稿/确认/发布版本、寄语修订、反馈凭证/反馈、设备会话和外部身份关联。报告不是第二套记分账。

P0终态是“有效卡即时+1、无教师待审、授权教师可纠错/直评、防重复、可回退”；无需等待AI或最终A4。P1终态是“有效来源自动形成六维、教师确认、隐私受控发布、真实家长反馈、真实AI要求和学生端/打印均按范围通过”。AI延期、家长身份变更或缩小字段须有明确业务决定，不能由开发默认省略。

### 1.2 硬边界与待输入

硬边界：一卡最多一次原奖励；更正只追加；同一证据不重复计分；跨学校/学生/职责不能越权；已发布快照不可被实时资料改写；新报告发布失败不破坏旧版。以上任一失败禁止放行，不以平均分或通过率抵消。

Spec没有给出SLA、实际并发、数据保留期限、法定合规认证、供应商数据处理条件、真实样例和团队配置。本计划不宣称取得这些结论。工程侧落实权限、必要输入、日志脱敏、可撤销凭证与审计；学校/数据负责人另确认保存、删除和外部传输政策。

将原12张业务决策拆成以下**输入集**，这是确认顺序建议，不是创建或关闭决策票：

| 输入集 | 最晚需要时点 | 必须明确 | 避免的无效串行 |
| --- | --- | --- | --- |
| G0：P0范围与权限 | P0实现前 | 学生身份/设备，教师/班主任职责，D/Z与子类份额，直评/纠错范围，旧卡首批处理，试点账号来源 | 不等荣誉权重、AI、A4；公共设备是否必需必须早定 |

### 1.3 容量验收提案

以下是**工程建议的测量包，尚非校方SLA或实测结果**：3000个不同学生、24000个评价单元；50个不同卡并发兑换，另100请求竞争同卡；受控内网兑换HTTP p95≤1.5秒、p99≤3秒；3000份预先确认报告的机器批量发布≤600秒，并持续显示进度。模型起草、教师审批等待不计入机器发布耗时。

执行前记录机器/数据库版本、CPU/内存、连接池、数据规模和网络条件；先测基线再由TL和学校确认容量门槛。不得使用“同一studentId写3000次”的旧例证明学校级容量。无论耗时目标是否调整，正确性硬边界保持不变。

### 2.2 合同冻结（本计划的工程选择）

所有新合同的Id使用字符串，金额/分值用精确十进制字符串，日期时间带明确时区；旧接口通过适配保留兼容。HTTP状态约定：未登录401、无权403、幂等载荷冲突/版本过期409、数据无效422、依赖不可用503。具体业务阈值由批准规则读取。

- **C0，20A提供：** `runRenovationScenario(id, options) -> { uiPassed, checks, artifacts, failures }`。复用既有运行器，新增`--scenario Rxx`筛选；只新建前缀受控的隔离库，子进程继承本次manifest，禁止回落业务库。迁移合同为 `applyRegisteredMigrations({connection,databaseName,dryRun,mode}) -> {applied,pending,failedStep,checksumMismatch}`，登记项为 `{id,checksum,up(connection,context)}`；各票只追加自己的步骤并登记。
- **C1，任教授权提供：** `resolveActorContext({userId,tokenHash,issuedRole},connection) -> ActorContext`；`assertScope({actor,studentId,termId,action,subjectCode?},connection) -> ScopeSnapshot`。ActorContext包含学校、当前角色/状态、职责及限定能力；敏感依赖不可读时503而非放行；签发角色与当前角色不同则401要求重新认证，不把旧Token静默升级为新角色。仅后续请求撤权立即生效；在途请求按已受理事务授权快照规则处理并审计。
- **C2，任教授权提供：** `withStudentTermMutation({actor,studentKey,requestKey,payloadHash}, mutate) -> {sourceRevision,result}`。同文件还提供 `withStudentTermsMutation({actor,studentKeys,requestKey,payloadHash},mutate) -> {sourceRevisions,result}`；单学生入口委托该入口。管理唯一连接/事务，按稳定键排序锁全部student_term_state，校验幂等，执行mutate后同事务增sourceRevision；幂等回放直接返回既有结果，不再次递增来源版本。扫码、奖励、更正、认定、正式故事、指标、导入、拟纳入草稿的反馈及学籍资料变化都接入；规则/模板版本另进入确认指纹。
- **C3，教师纠错提供：** `appendReward(connection,{studentKey,sourceKind,sourceId,amount,dimension,categoryId?,issuerTeacherId,initiatedBy,requestKey,payloadHash}) -> RewardReceipt`；`correctReward(connection,{eventId,expectedRevision,replacement,reason,actor,requestKey}) -> RewardReceipt`。RewardReceipt含eventId、entryIds、revision、amount、newlyApplied、replayed；amount描述该操作确认值，不冒充实时余额，实时净值另查。回放newlyApplied=false，前端不得再次庆祝加分。卡固定+1；允许改分范围来自规则。
- **C4，指标提供：** `IndicatorValue={indicatorCode,valueType,rawValue,value,status,sourceRef,revision}`；技术状态固定为RECORDED/MISSING/ABSENT/POSTPONED/EXEMPT/NOT_APPLICABLE；非RECORDED允许空值，何种状态满足必评门槛由G1规则明确，不偷偷重分配权重。导入返回`{batchId,revision,inputHash,expectedRevisions,validRows,errors,diff}`；提交只接batchId/预期批次版本，再从服务器重取输入和当前授权；整批或有效行策略均用C2多学生入口处理已确认提交集合，不私自逐行COMMIT；expectedRevisions是服务器保存的各来源预期版本，不由客户端重写。学籍/健康可用自己的适配器，禁止为了复用引擎而继承错误权限。
- **C5，自动六育提供：** `buildEvaluationSnapshot({studentKey,sourceRevision,policyVersion,connection}) -> EvaluationSnapshot`。结果含schemaVersion、sourceRevision、policyVersion、sixDimensions（值/状态/等级/分解/证据）、missingReasons；未配置无隐式默认规则。
- **C6，草稿提供：** `buildDraft({actor,studentKey,expectedSourceRevision}) -> Draft`；`confirmDraft({actor,draftId,expectedFingerprint,commentRevision}) -> Approval`。fingerprint由来源/学生资料版本、评分/指标/模板版本、寄语/纳入报告的家长修订版本共同生成。报告状态使用DRAFT/REVIEW/READY/PUBLISHED/SUPERSEDED。确认固定的是已保存的草稿快照，不是“现在再查一次”的动态报告。
- **C7，家长/AI各自提供：** `submitFamilyFeedback({credential,content,expectedRevision}) -> FeedbackRevision`；`requestComment({actor,draftId,expectedFingerprint}) -> Job`，完成时以原指纹CAS写建议。凭证只存哈希并限定学生/学期/动作，迟到AI不得覆盖人工确认。模型只消费可查看的必要事实包，不直接拼入故事全文、附件或原始寄语；文本中的敏感信息不得因已去掉姓名字段就认定全部脱敏。
- **C8，发布提供：** `publishOne(connection,{actor,reportId,expectedFingerprint,requestKey}) -> PublishItemResult`。锁同一student_term_state并验证确认指纹，同时比较当前有效规则/指标/模板/资料版本，不能只比较旧草稿自身哈希；读取已批准草稿而非另用pool重算；写发布快照/新当前版指针/旧版替代状态及审计同事务。批量使用持久作业逐份事务，结果仅状态/原因/允许标识。发布只增加reportRevision/版本指针，不递增sourceRevision，避免发布动作使自己的批准指纹失效。
- **C9，呈现提供：** `readPublishedReport({actor,reportId}) -> PublishedSnapshot`；`renderReport({snapshot,templateVersion,printMode}) -> HTML`。身份/正文/模板资源均取发布版本，打印时间独立。Timeline和首页只消费核算/来源DTO，不再算一遍正式分。
- **C10，18A提供：** `issueDeviceSession({deviceCredential,studentCredential}) -> RestrictedSession`，仅含兑换能力和短有效期；03通过C1识别此会话，18B负责清屏和切人。19只管理外部身份映射，不提供可签发登录会话的调试回调。

### 2.3 数据变更与并发规则

1. 增量迁移用有序、校验和、可重入的迁移登记；新建库与既有库升级都验证，不能只修改全量CREATE TABLE。DDL按可恢复步骤执行，不把多条DDL包装成“可整体回滚”。
2. 奖励根采用score_event，保存来源、学校/学生/学期、当前有效版本及金额；流水只追加。既有正向记录通过映射关联根，不能重记积分。来源/幂等唯一键包含学校与业务身份，复用请求键但载荷不同返回409。
3. score_record扩展来源与精确分值；卡/直评要求有效叶子，荣誉只要求T/M/L及来源引用，可无奖励叶子。旧荣誉生成列保留历史，新认定分/规则版本用普通列保存，不对生成列直接UPDATE。
4. 奖励分类树是学校范围的事件分类，报告指标是独立字典。旧全局树作为只读模板保留；新学校树必须有学校/版本唯一范围，卡和账本校验同校，禁止改全局树影响其他学校。
5. 典型写入锁顺序为学生学期状态→卡（若有）→奖励根/对应来源行→幂等记录。批量按稳定学生键排序；死锁只做有界整事务重试，复用请求键。发卡校级锁只用于批次生成，不搬到兑换热路径。
6. 所有影响草稿的来源写入与版本递增共用同一事务；不能只靠异步通知使确认失效。仍获准运行的LEGACY审批/导入也必须进入同一协议；若无法适配则先收口该旧写路径再启用，不留旁路。通知/缓存可延后，但发布必须检查权威版本。
7. 报告先保存批准快照，发布事务只验证并冻结；模型、PDF渲染、文件上传和大批量网络操作都在锁外。模板/字体资源留版本，保证旧打印正文可重现。
8. 发布后反馈留独立修订，可影响新草稿但不改旧发布版。新来源、基本资料或更正不得用恢复旧数据库的方式回退。

## 第3轮：依赖、关键路径与资源排期

### 3.1 修订顺序

先做20A兼容迁移/隔离入口，再并行任教授权和预分类制卡。任教授权后做教师纠错、故事、指标及按范围启用的学籍/身份预留；后二者依赖C1/C2但不等待P1。**教师纠错的C3交付后扫码/荣誉才能消费同一账本合同**。公共设备必需时18A先于扫码，18B在扫码后。

评价主链为“荣誉/故事/指标→自动六育→草稿”，然后AI、家长与发布并行，发布→阅读打印。学生首页在扫码/核算可用后整合真实成长。20B独立验证P0，20C再汇聚P1。

条件边：健康是必评来源时体测→自动六育；学科导入是某规则唯一来源时导入→自动六育；家长必填时家长→发布；试点缺基础账号时学籍→20B。真实钉钉若一期必须，身份预留票不足以解除条件，须明确新增真实集成范围。

### 3.2 估算方法与假设

## 第5轮：执行基线与放行

### 5.1 任务执行方式

文件归属、准确接口、逐票测试名/断言与运行步骤见[执行任务附录](2026-10-27-system-renovation-execution-tasks.md)。每个任务按“先写失败场景→跑出真实失败→最小实现→场景通过→评审并提交”执行。现有测试工具继续用，不额外引入与验收无关的内部镜像单测。

### 5.2 四道门

- [ ] **开工门：** G0/G1对应输入有责任人和实际答案；本票技术合同、迁移及所依赖节点已交付；ready-for-agent标签不是独立领取依据。
