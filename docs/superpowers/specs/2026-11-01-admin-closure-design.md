# 管理员端闭环补齐设计

日期：2026-11-01（Asia/Shanghai）　状态：设计待确认，尚未实施产品代码或数据库迁移。

## 1. 目标与已确认职责

从管理员建立班级、导入师生、为每班选择一位负责教师开始，经教师记录行为与导入成绩、学生自评和故事活动，到负责教师（班主任）审核、管理员统一发布、学生阅读期末六育报告，形成一条可追溯、可重复演示的真实业务链。

用户已确认：

1. 六育报告由班级的**负责教师（班主任）完成最终内容审核**；管理员负责发布前的数据完整性核对和统一发布。
2. **体测原始值已经由教师上传 Excel 实现，管理员不需要该功能。**管理员导航移除“体测原始值”，不新增管理员体测录入或体测模板。
3. 管理员界面延续学生端、教师端现有风格；用户同意打开浏览器预览设计。
4. **一个班级只选择一位负责教师，不提供学科任教配置。**该教师负责本班全部课程数据、行为评价、Excel 上传、材料处理和最终报告审核。
5. **班级详情移除“班级进度”页签。**只保留“学生名单／负责教师”两个页签；审核和发布进度在发布中心查看。
6. **不需要班级状态功能。**班级不设置启用／停用状态，不提供状态筛选或状态操作。
7. **班级 Card 面积约为原设计的四分之一。**采用约一半宽、一半高的紧凑卡片，只显示班名、负责教师、学生人数，点击查看详情。

设计者默认：保留现有 student／teacher／manager 三种角色，以“班级 → 一位负责教师”的关系授权，不再按学科分别授予班级权限；一位教师可以负责多个班级，建档时可以暂未分配，开展教师业务和发布前必须分配有效教师。本轮不增加自定义角色编辑器。所有测试使用虚构师生与独立数据库，不将旧版演示记录当作本轮验收结果。

## 3. 最终模块与三端数据交互

### 3.1 学籍与账号（增强）

- 学生、教师两个页签，按账号／姓名、班级和状态筛选；沿用模板下载、上传、差异预览、原子提交、错误清单和历史记录。
- 新增账号启用／停用、重置密码。重置时由管理员输入不少于现有长度要求的新密码，仅显示一次操作结果；服务端保存 bcrypt 哈希，日志与导入预览不返回明文或哈希。
- 启停和密码重置提高 token_version，旧登录会话立即失效。账号不物理删除，不在导入中跨角色改身份；本轮仅维护学生与教师账号，不提供管理员自停用入口。
- 已有账号导入保持密码不变；修改学生班级进入受控学籍更正流程，显示受影响班级和已确认人数。
- **数据关系：**users 负责身份；student_term_evaluation 负责本学期姓名／班级快照；school_class.responsible_teacher_id 负责本学期班级教师授权。学生仅见本人，教师只见本人负责的班级。账号停用不等于学籍转出，不能静默把该生从统计和发布名单中删掉。

### 3.2 班级管理（新增）

- 建立班级，字段为学期、年级、班号、显示名称和负责教师；支持模板导入、差异预览和批次提交。即使尚未导入学生也能先建空班级；教师可在账号导入后再分配。
- 班级列表采用紧凑 Card，显示班名、负责教师和在籍人数；支持年级与班名筛选，不展示任教学科数、审核进度、班级状态或状态筛选。
- 班级详情仅有“学生名单／负责教师”两个页签。负责教师页签只有一个教师选择框，最多选择一位启用教师；不再配置学科任教。选择前预览原教师、新教师及受影响学生，提交后旧教师立即失去该班数据权限，新教师获得本班全部教师业务权限。
- 调班先预览再提交：只改当前学期有效归属，保留该生来源事实和积分，重算原班、新班受影响排名，使相关审核确认失效；其他学期快照与已发布报告保持可读。发布准备或冻结期间禁止直接调班。
- 班级不设启用／停用状态或相关操作。班级编号有引用后不直接改，显示名称可以维护；历史学期班级按学期归属保留，不物理删除。
- **数据关系：**新 school_class 定义班级及其唯一负责教师；学籍快照提供名单。教师页面、上传、直评、材料审核、报告确认均由同一班级责任关系授权，不需要逐学科分配。更换教师使受影响的报告确认失效；已有卡片来源和所有权不自动转移，未使用旧卡按受控作废／更换流程处理。

### 3.3 学期配置与基础数据（增强）

- 展示学校当前学期、起止日期、采集截止、报告模板、规则版本及适用项目；保留报到日期和现有规则的差异预览、影响人数、版本校验、变更历史。
- 课程／六育字段和等级字典以现有 V2 policy 为准，管理员可以查看来源与说明；只开放现有业务允许修改的参数，防止界面改字典却没有对应计算或报表映射。
- 新增建立下一学期：填写学年、学期、名称与日期，复制选定班级及其负责教师，经预览选定学生名单后建立新的学期快照。评价数据、有效卡、审核确认和报告不复制；历史报表不重算。
- 切换当前学期必须校验同校唯一当前学期和日期有效性；存在发布准备批次时阻止切换。采集／核对／冻结／归档继续走现有阶段状态机。
- 原学期配置中的学科任教编辑入口移除；班级负责教师只在“班级管理”中维护，原区域保留引导链接。
- **数据关系：**academic_year 是规则、日期、阶段和版本的唯一来源；三端均读取同一学期配置。规则或名单改变后，相关确认必须失效，不能继续发布旧审核结果。

### 3.4 月度卡额度（保留并验证）

- 沿用 V2 课程卡额度、下发与追加机制，展示实际计划／制卡／领取情况；按教师与学期月份筛选。
- 只给启用且已分配负责班级的教师分配额度。课程／六育项目继续作为卡片分类，不作为教师任教学科授权；负责教师可处理本人班级的所有合法卡项目。不自动解锁已制卡计划，不重复发卡，不提供绕过教师、直接给学生制造过程积分的管理员入口。
- **数据关系：**管理员配额 → 教师计划／打印卡 → 学生扫码或教师直评 → 来源记录 → 排名和报告过程表现。两种记分路径都必须可追溯与防重复。

### 3.5 发布中心（增强）

- 四阶段明确显示“数据采集 → 班主任审核 → 报告准备 → 全校发布”；统计全校在籍人数、缺项人数、有效确认数和当前发布数。
- 按班级展示卡片或表格，缺项清单包含学生、项目、缺失原因与责任角色；可筛选和导出。管理员只看发布核对所需的完整性、来源和状态，不开放学生私有作品正文的批量浏览。
- 内容审核留在教师端：班级负责教师查看本班完整版报告、处理全部项目数据、核对及确认。数据改变后确认失效，管理员看到“需重新审核”。
- 管理员完成完整性核对后准备全校报告；保留准备进度、失败恢复、取消批次、统一发布确认和版本信息。预检未通过时后端也拒绝发布。
- **数据关系：**读取与教师端一致的 completion／fingerprint；发布创建 term_report 冻结快照并激活学期发布版本。学生只读本人当前已发布版本，教师仅阅读本人负责班级的报告。

### 3.6 数据统计（新增）

- 全校／年级／班级筛选；展示在籍人数、各六育维度的已采集／应采集数量与完成率、待处理材料数、班主任有效确认数和发布数。
- 显示六育维度进度条、班级明细、缺项类型分布；可展开定位到责任班级和原业务入口。
- 支持导出当前筛选结果的 CSV，采用与屏幕相同的服务端查询口径，包含学期、统计时间与版本。导出逐项处理 CSV 公式注入风险。
- **口径：**分母为该学期有效在籍名单与适用项目；0 是有效数值，空值为未采集，不适用不计分母；分母为 0 显示“不适用”。不得将不同维度分数混合计算虚构总分。当前采集进度和已发布快照分别标注，不混用版本。
- **数据关系：**复用有效学籍、V2 统计及 completion 服务；管理员看全校汇总，教师看职责范围，学生看本人数据，不扩大学生数据权限。

### 3.7 操作记录（新增）

- 按学期、操作者、动作类型和时间查询；覆盖师生／班级导入、账号动作、调班、负责教师调整、规则变更、额度、确认与发布等已有和新增可审计动作。
- 列表显示操作者、对象、时间、结果和批次；详情显示安全的前后差异、原因和关联记录，支持分页和安全 CSV 导出。
- **数据关系：**复用 evaluation_source_record 的 AUDIT／BATCH 事实，不再另造一份会与业务提交脱节的日志表。权限和敏感字段脱敏由服务端执行。

## 5. 界面设计

设计方向：沿用“云美”现有温和校园手账风格，米白底、浅绿分区、墨绿主操作、宋体品牌标题与现有中文正文字体；不引入新 UI 框架或在线字体。

最终导航七项：**发布中心／学籍与账号／班级管理／月度卡额度／数据统计／学期配置／操作记录**。管理员默认进入发布中心，保持原操作习惯。

| 页面 | 主体布局 | 核心交互与反馈 |
| --- | --- | --- |
| 发布中心 | 顶部四指标 → 四步阶段 → 班级进度表 → 缺项与发布批次 | 缺项可展开；准备、恢复、发布显示进度和明确禁用原因 |
| 学籍与账号 | 学生／教师页签 → 筛选 → 账号表 → 导入区域 | 行内启停／重置；模板上传后差异面板；输入冲突时保留草稿 |
| 班级管理 | 建班／导入 → 年级与班名筛选 → 紧凑 Card → 详情面板 | 每卡面积约原版 1/4；只显示班名、负责教师、人数；详情只含学生名单／负责教师，不设班级状态和进度页签 |
| 月度卡额度 | 月份与科目筛选 → 教师额度 → 下发预览 | 展示分配数、计划数、实际制卡数；追加原因与提交结果 |
| 数据统计 | 学期／年级／班级筛选 → 六育进度 → 班级统计表 | 指标可定位缺项；同口径导出；区分当前与已发布数据 |
| 学期配置 | 学期信息 → 报到与采集规则 → 新学期与历史 | 修改前展示影响；建立下一学期需预览复制范围 |
| 操作记录 | 操作者／类型／日期筛选 → 时间顺序列表 → 差异详情 | 可回看关联批次，不显示密码、令牌、文件私有路径 |

所有页面提供加载、空列表、无搜索结果、权限错误、提交失败与成功状态；按钮有处理中状态；对话框支持键盘和焦点返回。桌面按 1440px 核验，窄屏按 390px 核验，表格可在容器内横向滚动，页面不溢出。

浏览器原型是**标注为示例数据的可点击设计稿**，只用于确认布局与职责，不连接业务库，不作为第 2 步正式产品实现或第 4 步验收完成的证据。

## 6. 数据库与迁移

只新增一张有实际建模必要的表 `school_class`，避免在 users、任教、学籍快照之间用隐含的班级组合代替班级实体。

| 字段 | 设计 |
| --- | --- |
| id | BIGINT UNSIGNED 主键 |
| school_id、term_id | 学校和所属学期；同校复合外键指向 academic_year |
| grade、class_no | 正整数；同校同学期组合唯一 |
| display_name | 可维护的班级名称 |
| responsible_teacher_id | 可空 BIGINT UNSIGNED；同校复合外键指向 users；只可选本校启用教师 |
| revision | 乐观锁版本，默认 1 |
| created_by、updated_by | 同校操作者引用，可为空以支持历史回填 |
| created_at、updated_at | UTC 时间 |

不另建学籍、任教、评价事实、审核或审计影子表。负责教师直接从 school_class.responsible_teacher_id 读取，人数从学期有效学籍统计，班级表不缓存派生人数。不增加班级 status 字段。增强版 V2 以班级负责教师为唯一教师授权来源，不暗中创建一套逐学科任教行；旧 teacher_teaching_assignment 只用于历史版本兼容与迁移核对，不再作为增强版 V2 的权限来源。

迁移要求：

1. 独立脚本默认 check，显式 apply 才写。核验目标库名、连接目标、版本与结构；发现未知或冲突结构停止。MySQL DDL 不是整体事务，必须输出逐步进度，失败后可重入。
2. V1 六表、V2 七表、管理员增强八表有明确契约。同步更新 `runCoreMigrations`、V2 migration 和 schema 描述，不简单取消表数／结构校验。保留已有 V1 回归与旧报告解释能力。
3. 对 V2 库追加班级表，根据学期学籍和旧任教中的合法班级并集回填。旧关系中存在唯一启用班主任时可迁为负责教师；多人冲突先报告，无班主任则留空待管理员选择，不按学科任意猜人。不改变原师生 ID、密码或历史报告，不自动改未知旧 44 表库。
4. 新库按 V1 → V2 → 管理员增强顺序初始化；空库、已有 V2、已升级、部分失败、错误目标和重复 apply 都要验证。
5. 班级引用和负责教师由统一业务服务验证；学籍、教师业务和权限读取不得绕过班级责任关系。教师名单、课程卡、Excel 字段许可、直评、材料审核、寄语、工作台和报告确认都需切换到同一负责教师口径；只改管理员选择框不足以完成变更。历史 V1 仍使用原解释器和原授权契约，不为适配新界面重写旧事实。
6. 测试／演示库实际执行迁移并 seed；当前开发库先只读审计，核实为本机目标且备份成功后执行追加迁移。真实生产或无法确认归属的目标只交付检查结果和脚本。
7. 不提供自动 DROP 班级表的回退。应用回退依赖上线前备份与契约版本；新增表可保留，旧版启动前恢复对应契约，避免“删表回退”丢失新数据。

新表测试数据至少覆盖：四年级 1 班、四年级 2 班、五年级 1 班、一个空班、一个历史学期班，以及另一学校的同年级同班号；覆盖单教师负责多班、尚未分配教师和跨校教师被拒。真实闭环库仅 bootstrap 管理员与学期，师生、班级和负责教师通过实际页面建立，不通过 seed 预先制造闭环结果。

## 7. 闭环验收与逐项修复

主场景采用当前 V2 真正适用的完整字段集合，准备两班至少四名学生、两位班主任和一位无关班级教师；新人员账号统一为虚构演示账号。预期报告结果独立记录在夹具中，不从程序实际结果反抄成预期。

| 序号 | 角色与操作 | 预期结果与必要证据 |
| --- | --- | --- |
| 01 | 管理员建立／导入班级 | 空班可见，重复预览无重复班；新表实际新增正确 |
| 02 | 管理员导入教师、学生 | 预览不改变业务名单；提交后账号和学期快照正确；错误文件整批拦截 |
| 03 | 管理员为每班选择一位负责教师并配置额度 | 所选教师获得本班全部适用项目权限；无关教师无权访问；同班只有一位负责教师，不需要任何学科任教配置 |
| 04 | 教师登录并记录日常行为 | 新导入学生出现在正确班级；直评事实与积分一致，可追溯 |
| 05 | 教师制卡，学生登录扫码 | 真实凭证可预览、领取；重复领取不重复入账；非本班领取被拒 |
| 06 | 学生完成自评、故事与证书提交 | 本人进度更新；故事三条路径和证书状态按现有业务落库；测试依赖若为替身明确标注 |
| 07 | 教师 Excel 上传成绩与体测，审核材料、填写寄语、结算 | 数据落到正确格子，0 值有效；管理员端没有体测录入入口 |
| 08 | 班主任检查完整六育报告并确认 | 适用项齐全后确认有效；先演示缺项阻断，补齐再确认 |
| 09 | 修改一项已确认数据 | 班主任确认失效，管理员发布被阻止；重新审核后恢复 |
| 10 | 管理员核对统计、准备并统一发布 | 统计分母与数据库名单一致；全校完成一个发布版本，无半发布可见状态 |
| 11 | 学生查看本人报告，教师回看本班报告 | 真实报告六育各项与独立预期逐项一致；打印布局和冻结版本正确 |
| 12 | 退出、重登及负向权限 | 未登录、跨角色、跨校、跨班、他人报告均拒绝；停用和重置后旧 token 失效 |

补充回归：调班前后排名与审核失效、导入幂等、预览后数据变化的 409、空班、无负责教师、负责教师更换后旧教师立即失权、新教师可上传全部适用字段、无班级状态和学科任教入口、全部不适用、分页与导出范围、规则版本兼容、发布冻结、旧版本报告读取以及 390px 紧凑卡片布局。

执行顺序为针对性服务／迁移测试 → 前端模型与现有必要回归 → lint/build → 全字段集成闭环 → MCP 浏览器重演。失败逐项记录“复现、原因、修复、复测命令／浏览器步骤、证据路径”；有关用例通过后再运行受影响回归。只有必要项全部通过才标注“闭环测试通过”。

本轮不部署、不合并，不恢复当前工作区已删除的旧入口；已有未提交的学生端／教师端改动作为现状保留，在其基础上追加可审查变更。
