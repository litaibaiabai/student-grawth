# 六育评价系统需求差异与修改方案

> 最新业务基线为[学校期末报告核心工作流精简方案](2026-10-28-term-report-core-workflow-design.md)，根据用户新PDF和六种来源收敛为6张核心业务表。本文保留原系统差异证据；旧来源、102项布局和多表建议应按最新方案更新。

> 数据库结构更新：按用户最新要求改用学生学期宽表和精简业务表。差异分析仍作参考，但此前的指标字典/竖表及多表新增建议已由[六板块宽表与最少数据表设计](2026-10-28-wide-table-simplification-design.md)替代。

日期：2026-10-28。核查代码基线：`07ae1c2`。状态：供评审的修改方案，尚未实施。

本方案按三个交付问题组织：数据库实际缺少什么；功能模块分别删除、修改、新增什么；哪些界面需要重构。沿用现有 React、Express、MySQL，复用已存在的账本、权限、草稿与快照能力。

六板块的数据结构及来源已另整理为[六板块评价数据结构与来源](../../六板块评价数据结构与来源.md)，含共用表字段、逐板块来源、负责角色及全部展示位置的映射台账。涉及评价视角、重复特长项目和文字来源的细化以该文件为准。

## 1. 核查结论与依据

**当前系统具备一部分基础表和服务，但本次需求尚未形成业务闭环。主要工作是调整数据模型和主业务流程，再重构操作界面与报告。**

本次已只读连接 `backend/.env` 配置的数据库，读取 `information_schema.COLUMNS` 和 `STATISTICS`，确认共有 **44 张表**。没有读取师生业务记录，没有修改数据库。实际字段与索引清单见同目录 `2026-10-28-current-database-schema.json`。因此，下文的“已有字段”来自实库元数据；“功能已接通”来自当前路由和调用链，两者分别判断。本次未运行浏览器业务流程或数据库写入测试。

关键事实：

1. 正常调度器调用 `cardAllocationService.reconcileMonth`，生成卡的 `category_id` 仍为空。已有 `rewardCategoryService.generatePreclassifiedCards` 没有接入正常发卡入口，不能据其服务测试认定“制卡时定分类”已经交付。
2. 管理员已控制学科月总数，但老师不能在个人总额度内按学科、班级和细分方向编排；卡片也没有生成时的班级归属。
3. 管理员六育终测导入仍可使用。实时综合评价和报告核算均仍读取 `student_dimension_score`。
4. 年级指标、健康记录、报告草稿、家长寄语等表确实存在；报告草稿未收集指标明细、健康、读听讲评价及结构化学生自述。
5. 管理员仍勾选学生发布，服务逐学生提交，允许部分成功；不是统一的全校发布。
6. HTML 打印已存在，方向可以复用；实际页面仍是总分、维度分、评语等旧版，不是指定学校正反面模板。

### 1.1 需求材料的口径问题

| 问题 | 核查结果 | 本方案处理 |
| --- | --- | --- |
| 74 项评价数据 | 本次列出的领域数量相加为 **68**，不是 74 | 保留“承载 74 项”的目标，先做可配置指标模型；逐字段映射最终以原始 .doc 为准，不能自行补造六项 |
| 体测“共 6 项” | 身高、体重、左右视力、跳绳是 5 个原始值；再加体测水平、过程表现，实际为 **7 个独立值** | 按 5 个原始值和 2 个评价项承载；确认学校是否将左右视力合计为一类 |
| 历史字段说明 | `userAdvice.md` 是 82 个 Excel 表头、扣除前 8 项后的 74 项；本次是 80 个 Word 合并字段扣除 6 项 | 是两种不同统计口径，不能直接照搬旧的 74 项字典 |
| 指定报告附件 | 用户随后提供六板块测评明细图片，已保存为 `docs/ui-prototype/semester-assessment/reference.png`；正面图、原始 .doc/.xls 尚未取得 | 测评明细布局和可见栏目按该图确定；完整合并字段及报告正面继续对账，见第 11 节 |
| 待确认 12、14 | 本次未附完整待确认列表；历史材料中的第 14 条是 AI 学期寄语 | 雷达图和健康数据来源保留决策项，不把缺失材料推断为已批准规则 |

“74 项”是报告能力和字段映射目标，**不等于给学生表增加 74 列**。一个指标还可能同时有自评、他评、文字描述，业务记录数量会多于指标数量。

## 2. 逐项需求差异

| 需求 | 当前实际实现 | 结论 | 修改方向 |
| --- | --- | --- | --- |
| 管理员统一下发总卡量 | 管理员按学科配置 `monthly_total`，按教师主教学科自动生成整份卡 | 部分具备，权限分工不同 | 管理员下发教师额度；教师在额度内分配，不自动替老师决定细类和班级 |
| 制卡时确定方向和子类 | 正常生成器只写方向，子类为空；另有未接通的预分类生成服务 | 主流程不符合 | 确认教师分配计划后生成，每张卡绑定有效叶子分类及版本 |
| 扫码后自动加分 | 有 `category_id` 时进入即时兑换；正常生成的无分类卡仍进入待审核 | 部分具备 | 新卡统一即时入账；旧卡按历史协议隔离 |
| 多班一次生成、按班分文件 | 月度打印任务按教师拼成一个 PDF | 缺失 | 每个教师的每个班独立 PDF，一次任务输出 ZIP 和清单 |
| 按班框定总张数 | 卡和分配表没有班级字段，只有领卡学生当时班级 | 缺失 | 分配明细按班保存数量；卡生成时冻结所属班级 |
| 学生直接填写、粘贴月度故事 | 文本框、草稿、提交和教师终审已存在 | 基本符合 | 保留，补手机钉钉登录；不增加 Word 上传 |
| 云美小故事只接最终成绩 | 没有专用成绩接收记录和外部故事接口 | 缺失 | 单独接收外部最终结果并保留版本、来源，不接管小程序入口 |
| 读、听、讲三项及各自经历描述 | 月度故事只有一个 `teacher_score`、一个评语 | 缺失 | 三个指标，每项独立评价和实践描述；与月度作文并存 |
| 取消管理员六育终测导入 | 页面、预览、提交和批量导入仍支持 `DIMENSION` | 不符合 | 服务端禁用新模式终测写入，历史数据只读留档 |
| 自动汇总六育结果 | 两套核算都依赖终测表，只对故事和过程/荣誉作部分聚合 | 不符合 | 统一以分类积分、指标、正式学科结果、荣誉及故事来源核算 |
| 健康与体测数据 | 表有身高、体重、左右视力；无 1 分钟跳绳；健康服务未接业务路由 | 部分底座 | 增加跳绳和来源字段，接通授权录入/导入；两项体测评价进指标表 |
| 全校一次性发布 | 必须提交学生列表；逐人事务，部分成功 | 不符合 | 服务端确定全校应评名单，统一校验并执行学校级发布 |
| 按学校正反面模板、移动竖屏 | 网页仍是总分、雷达和文化课列表；打印另有旧模板 | 不符合 | 同一报告模型，两套响应式/打印样式；A4 正反面明确分页 |
| 74 项评价呈现 | 有泛化指标表，无完整模板字典、来源映射与快照收集 | 未形成闭环 | 字段字典、录入、来源校验、快照、渲染、缺项检查一起补齐 |
| 星级与字母双轨 | 字典能记录 `star/grade`，实际报告多处硬编码优秀/良好/合格 | 部分底座 | 每项声明显示制式和允许值，星级 1—3，字母合法值待校规确认 |
| 自评、他评分列保存 | 指标唯一键仅“学生+学期+指标”，再次写入会覆盖同项 | 不符合 | 增加评价视角及来源，修改唯一键；自评和他评独立保存 |
| 云美少年学生自述 | 报告表只有一个 `student_statement`，没有学生填写该区的业务链 | 缺失 | 增加结构化学期自述记录及学生页面，完整冻结进报告 |
| 学期寄语、家长寄语、开学月日 | 教师及家长寄语已有底座，开学日期没有专用字段 | 部分具备 | 教师寄语以“学期寄语”展示；新增下学期报到日期并冻结 |

## 3. 数据库修改清单

本节区分“没有字段”“已有字段但未使用”“应增加一条字典/数据记录”。字段名、类型为本方案建议，最终迁移要匹配现有外键的有无符号和长度。

### 3.1 卡片额度与班级分配

| 表 | 实库已有 | 建议增加或修改 | 目的 |
| --- | --- | --- | --- |
| `card_quota_rule` | 学校、学期、月份、教师、`quota_n`、`allocation_json`、配置版本、创建人 | 复用为管理员额度主表；增加 `status VARCHAR(16)`、`revision INT`，不另建同义额度表 | 恢复“管理员核定教师总量”的业务角色；不能让老师改 `quota_n` |
| `card_allocation` | 每教师每月一条，单个学科和策略；`monthly_total`、六维计数、状态 | 增加 `quota_id BIGINT UNSIGNED`、`plan_revision INT`、`request_key VARCHAR(128)`；`subject_id`、`subject_name`、`policy_version_id` 对新模式允许 NULL；扩展状态包含草稿/确认 | 作为教师当期计划主表；具体学科、班级、分类下沉明细，摆脱单一主教学科限制 |
| **新增 `card_allocation_class`** | 不存在 | `id`、`school_id`、`allocation_id`、`grade`、`class_no`、`class_name_snapshot`、`class_total`、`revision`、时间戳 | 单独保存教师为每个班指定的总卡量，作为班内细分的上限和对账基准 |
| **新增 `card_allocation_detail`** | 不存在 | `id`、`school_id`、`allocation_id`、`class_allocation_id`、`subject_id`、`category_id`、`category_version`、`card_count`、`revision`、时间戳 | 每行确定该班某学科某叶子分类的卡量；不能只记录细分数量而丢掉已指定的班级总量 |
| `reward_card` | 已有方向、`category_id/name/version/path`、固定分值、令牌和分配 ID | 增加 `allocation_detail_id BIGINT UNSIGNED NULL`、`issued_grade INT NULL`、`issued_class_no INT NULL`、`issued_class_name VARCHAR(64) NULL`、`issuance_mode VARCHAR(16)` | 保存生成时的班级归属和新旧模式；分类字段必须在生成时写满，不能重复新增同义分类列 |
| `card_print_pack` | 单文件路径、文件哈希、清单 JSON、模板版本 | 增加 `teacher_id BIGINT UNSIGNED NULL`、`artifact_type VARCHAR(16)`，现有文件路径可保存 ZIP | 一位老师的全部班级形成一个可下载任务；管理员可代制、代下载 |
| **新增 `card_print_pack_file`** | 不存在 | `id`、`pack_id`、`teacher_id`、`grade`、`class_no`、`file_name`、`file_path`、`file_sha256`、`card_count`、`manifest_json`、`status` | 一个班一个文件；记录每份文件实际包含哪些卡，支持恢复和重印 |

约束与规则：

- 管理员额度沿用 `quota_n`，各班 `class_total` 加总不得超过额度；生成前每班细分 `card_count` 加总必须等于本班 `class_total`。校验与生成共用锁和事务，不能仅靠前端剩余量。
- 当前 `card_allocation` 的唯一键为 `(school_id, teacher_id, month_key)`，建议加入 `term_id`；班级分配唯一范围为分配与年级班号，细分唯一范围包含班级分配、学科、分类和版本。重试请求不得重复占额、重复制卡。
- 当前 `subject_id`、`policy_version_id` 有索引/外键依赖，放宽 NULL 时同步调整迁移和旧模式兼容，不能只改服务参数。
- `reward_card` 新模式在服务端要求有效叶子分类、班级和分配明细非空；历史卡保留 NULL，不能全表强制 NOT NULL 后破坏旧数据。
- 当前没有独立班级主表，首版沿用 `school_id + term_id + grade + class_no` 和班名快照，不无依据增加 `class_id` 外键。
- **建议规则**：已生成卡占用额度，重印不占新额度；作废不自动释放额度，补发须管理员明确调整。旧版“主教学科比例自动编排”仅保留为历史记录，不能继续生成新模式实卡。
- **待学校确认**：班级归属是否同时限制兑换人。建议同班学生才可领取；如只要求追溯而允许跨班，应只记录来源班级，并明确告知，不暗中强制。

### 3.2 指标字典与自评他评

| 表 | 实库已有 | 建议增加或修改 | 目的 |
| --- | --- | --- | --- |
| `grade_indicator_definition` | 指标代码、名称、六育方向、`value_type`、单位、必填、年级学期 | 增加 `definition_version VARCHAR(32)`、`subject_code VARCHAR(30) NULL`、`report_section VARCHAR(32)`、`report_field_key VARCHAR(128)`、`sort_order INT`、`allowed_values JSON`、`perspectives JSON`、`source_policy JSON`、`aggregation_rule JSON NULL`、`display_config JSON` | 声明属于哪个学科/版块、值制式、合法值、需要自评还是他评、来源及汇总规则 |
| `student_indicator_value` | 原值 TEXT、`typed_value VARCHAR(255)`、数值、状态、评定人、修订号 | 增加 `definition_version`、`perspective`、`evaluator_role`、`instance_key`、`source_type/ref/version`、`evidence_refs`、确认人和确认时间；短等级用原 `typed_value`，星数/数值用 `numeric_value`，完整描述独立记录并用 `raw_value TEXT` | 同项自评/他评独立；多个特长项目可扩展；评分与文字分别追踪来源，无须强制另增 `narrative_text` |
| **新增 `student_indicator_value_revision`** | 现表只覆盖当前值、递增 `revision`，无历史值表 | 值记录 ID、修订号、旧/新值、视角、来源、操作人和时间；与主键类型一致 | 查询被修改前的值及来源，支持报告追溯 |

必须替换现有唯一键 `(student_id, term_id, indicator_code)`，建议为 `(school_id, student_id, term_id, definition_version, indicator_code, perspective, instance_key)`。`SELF` 为学生自评，`OTHER` 为对外展示的他评/教师评价，`NONE` 为非评分事实或描述；`evaluator_role` 另记实际角色。普通指标实例为 DEFAULT，体育/艺术特长使用稳定项目实例键；首版每视角每实例一个当前正式值。若要多人互评，应另建明细并确定聚合，不能让多人反复覆盖。

指标定义表的现有唯一键 `(school_id, term_id, grade, indicator_code)` 也要加入 `definition_version`。已经用于发布的字典版本保持只读，新定义发新版本，不能沿用当前按代码覆盖定义的写法。模板字段映射引用明确的定义版本，自评/他评两格都须能定位到相应值。

以下不需要建新列，而需要初始化**指标定义记录**及模板映射：

- 日常行为八项：有礼貌、讲文明、讲信用、负责任、有爱心、守规则、善交流、会合作；每项 `SELF/OTHER` 各一值。
- 道法、语文、数学、科学、英语、体育、音乐、美术、信息科技、劳动、综合实践、地方课程的各明细项；完整名称和数量按原报告逐字段对账。
- `HEALTH_TEST_LEVEL`、`HEALTH_TEST_PROCESS`：体测水平、体测过程表现，采用星级。
- 读、听、讲分别有独立评价指标和实践描述指标，如 `STORY_READ_ASSESSMENT`、`STORY_READ_EXPERIENCE`；它们可分别来自外部最终成绩与本地确认文字，不能用一个故事总分填满三格。
- 音乐、美术、体育技能特长的评价项，依模板声明双视角；特长项目名称本身使用文本指标，不混在星级值内。

同一领域内“学业水平用 A”与“某些项目用星级”都由逐项字典确定，不能按整门学科统一强转。`star` 校验 1—3；`grade` 的 A 以外允许集合、等级边界需学校确认。缺失、不适用、免测和真实零值分别记录，不默认显示一星或零分。

API 还须校验指标是否属于该校、该学期、年级和教师任教学科。当前 `saveStudentIndicatorValues` 主要校验班级，不核对字典允许值；`getStudentIndicatorValues` 对学生身份缺少“只读本人”分支。新增学生自评前应先补齐读写权限，不能依赖隐藏入口。

### 3.3 身体健康与体测

| 表 | 已有能力 | 需要补齐 |
| --- | --- | --- |
| `student_health_record` | `height`、`weight`、`left_vision`、`right_vision`；另有肺活量、50 米跑、坐位体前屈、免测类型、测试日期、导入人和批次 | 新增 `jump_rope_1min INT UNSIGNED NULL`、`source_type VARCHAR(32)`、`source_ref VARCHAR(128)`、`source_version VARCHAR(64)`；保留原字段，不删除学校可能仍使用的旧体测原值 |
| `health_import_batch` | 预览、差异 JSON、批次状态和载荷哈希已有 | 视数据来源补充来源标识和预期版本校验；接通控制器、路由及教师界面 |

体测水平、过程表现保存到指标结果表，不在健康表重复存第二份正式结果；报告生成时统一读取。身高、体重、视力只作原始值展示，不能直接折算为行为奖惩积分。视力目前为字符串，必须明确采用小数视力还是其他标准后再做有效值校验，不能直接套用星级。

**来源建议，未视为学校已决定**：体育教师确认体测评价；学校指定体育教师或健康数据负责人导入/录入原始值，也可由学校健康平台同步。取消六育终测导入不等于禁止输入健康原始数据。本次不擅自赋予所有管理员健康明细访问权。

### 3.4 月度故事与外部故事成绩

现有 `story_submission + material_revision` 继续承载本系统月度故事正文、修订与教师终审，不要求为“读听讲”增加三套月度故事投稿，也不把本系统写作文等同于小程序三项成绩。

建议新增 **`external_story_result`**：

| 字段 | 建议类型 | 用途 |
| --- | --- | --- |
| `id / school_id / term_id / student_id` | 匹配现有主键类型；`student_id` 可空 | 校内学生和学期定位；待匹配状态允许尚未确定校内学生，匹配成功前不参与评价 |
| `provider / external_record_id / external_version` | VARCHAR | 标识云美小故事最终结果及更正版本，重发不重复计入 |
| `external_student_ref` | VARCHAR(128) | 保存外部学生标识供匹配，不用姓名直接猜测校内账号 |
| `result_code` | VARCHAR(32) | 明确是总结果、读、听、讲，禁止擅自拆分 |
| `raw_value / value_type / score_value / grade_value` | TEXT / VARCHAR / DECIMAL / VARCHAR | 接收实际提供的最终成绩及标准化值；按用户要求不接收小程序原稿或实践描述 |
| `status / source_ref / received_at / confirmed_by` | VARCHAR / VARCHAR / DATETIME / ID | 区分待匹配、有效、被更正，记录接收确认 |

唯一约束包含学校、提供方、外部记录 ID、外部版本和结果代码。接口或批量文件两种接入方式中，实施前只选择学校实际可提供的一种；两者都必须保留来源和更正机制。

读听讲的正式报告值仍统一落在/映射到指标结果；外部记录作为证据源，不再另算一遍奖励积分。若小程序只提供一个总分，该总分不能复制为读听讲三项；三项由相应教师补充评价，具体来源优先级需学校确认。

### 3.5 学生自述、开学日期、报告快照与规则

| 表 | 已有字段 | 建议增加或修改 |
| --- | --- | --- |
| **新增 `student_term_reflection`** | 不存在；`term_report.student_statement` 只是一个报告文本列 | 学校/学生/学期、`conduct_text`、`wisdom_text`、`health_text`、`art_text`、`labor_text`、`semester_highlights TEXT`、`next_term_goals TEXT`、状态、修订号、提交时间；五方面收获活动及总体收获目标分别保存 |
| `academic_year` | `start_date/end_date` 是当前学期校历 | 增加 `next_term_registration_date DATE NULL`、`evaluation_mode VARCHAR(16)`；日期在报告上显示月日，模式标识历史和新体系，不能把当前学期开始时间当作下学期报到时间 |
| `student_report_draft` | `teacher_comment`、`parent_comment`、`draft_snapshot`、确认人、来源版本、指纹 | 增加 `template_version VARCHAR(32)`、`definition_version VARCHAR(32)`；扩充快照内容，无须再增加同义“学期寄语”列 |
| `term_report` | `snapshot_json`、教师寄语、学生单段自述、家长寄语、版本、发布状态 | 增加 `template_version`、`definition_version`、`publish_batch_id`；完整结构化自述、明细、日期进入快照，原单段 `student_statement` 留作历史兼容 |
| `student_evaluation_snapshot` | 六维 JSON、过程/荣誉摘要、规则和来源版本；总分与均分 NOT NULL | 增加明细/证据引用 JSON 或规范化快照结构；若学校取消总分，总分和均分改可空，不能填 0 伪装已算 |
| `comprehensive_score_rule` | 仅六维/过程/荣誉三项权重与封顶目标 | 增加 `engine_version`、`definition_version`、`rule_config JSON`，表达各项来源、等级边界、聚合和适用性；不擅自沿用旧权重 |
| **新增 `report_template_version`** | 没有报告模板注册表；卡片模板版本不能代替报告模板 | 学校、模板版本、状态、正反面字段映射、字典版本、版式配置及发布时间 |

建议报告快照包含 `student`、`term`、`templateVersion`、`definitionVersion`、`indicators`（含视角、文字、来源）、`health`、`storyAssessments`、`studentReflection`、`teacherComment`、`familyMessage`、`nextTermRegistrationDate`、`evaluationSummary`、`sourceRevision`。这里只定义数据结构，不创建业务代码。

新增内容必须参与草稿确认指纹；报告生成时按各来源的有效正式版本取值，不能把 `subject_score` 中同一学科的历史多个 `version` 全部当作当期正式成绩。指标、故事终审、外部结果、自述、家长寄语、报到日期和模板/规则变更均应接入版本失效机制；不能只在修改积分时递增 `source_revision`。

教师寄语和家长寄语有现成存储基础，不应被列为“数据库完全缺失”。本次真正缺的是分项自述、开学日期、完整明细快照、模板映射和输入/确认链路。

### 3.6 全校发布

扩展 **`report_publish_batch`**：增加 `scope VARCHAR(16)`（新模式固定 SCHOOL）、`status VARCHAR(24)`、`request_key VARCHAR(128)`、`roster_hash CHAR(64)`、`expected_count INT`、`source_manifest JSON`、`activated_at DATETIME`、`error_summary JSON`。现有 `grade` 留作历史字段，不对新模式开放按年级发布。

新增 **`report_publish_item`**：批次 ID、学生 ID、草稿 ID、预期来源版本、预期指纹、准备状态、暂存报告 ID、失败原因。它保存批次目标与版本清单，不再让前端提供任意学生列表。

**建议的一次性语义**：全校有效学生作为一次发布对象；先完成全体准备，全部通过后统一可见。使用“逐份准备 + 单批次激活”避免全校长事务；学生和打印的所有查询均须检查批次已激活，准备中不得可见。若学校允许全校按钮只发布已完成学生而跳过缺项者，应作为另一项明确决策，不能默认沿用当前部分成功行为。

校验全校准备状态时，名单、年级适用项、免测处理、指标字典版本、源数据版本、班主任确认及模板版本须统一。准备到激活期间建议建立学期发布锁，所有纳入报告的写入都遵守锁；激活前再次核对名单与版本。原已发布批次继续可见，新批次失败不撤掉旧报告。不同学生的报告版本号仍独立，不必因统一发布强行相同。

### 4.2 应修改的模块

1. **配卡与打印**：管理员额度下发、教师编排、按班计数、分类冻结、一次生成、分班文件、重试与重印。
2. **扫码和公共设备兑换**：统一走新卡即时入账逻辑，幂等防重；读取卡的固定分类及班级信息，不接受客户端另传目标分类覆盖。
3. **指标评价与学科成绩**：接通教师逐项评定，支持星级/字母/描述；原 `subject_score.grade_label` 已有，需实际写入并优先使用，不重复新增等级列。
4. **评价引擎**：实时评价和报告使用同一来源聚合服务；当前实时取最新终审故事、报告取多篇均值的差异一并消除。无数据与零值分开；健康原值不计奖励积分。
5. **报告草稿**：把指标、双列、健康、三项故事、自述、日期都收集到草稿；任何来源变化令确认失效；班主任确认最终学期寄语。
6. **发布**：全校名单由服务端确定；先检查再全校统一激活；禁止发布服务自动代班主任确认。
7. **故事与身份**：保留文本输入，补小程序最终成绩接入；钉钉从身份关联预留升级为真实登录和登录后返回原页面。
8. **权限与进度**：按学校/学期/班级/学科/评价视角验证，统计应完成的必需项，不能把“该生有任意一条指标”当成完成。

## 6. 三条必须修正的底层逻辑

### 6.1 “服务存在”不能等于“正常入口可用”

- `rewardCategoryService` 目前没有进入调度链，且硬编码只造 D/Z 并近半均分；不能直接替换入口后声称满足老师自主分类。本次要求六育方向和子类可确定，允许范围应按最新校规配置，不照搬旧服务限制。
- `healthImportService` 只有服务及服务级测试，当前 `routes/api.js` 没有健康业务路由，教师也无正式健康界面。
- `reportRenderService` 有另一套 A4 HTML，但当前下载入口在 `reportController.exportReportHtml` 内直接拼 HTML，修改前者不会改变实际用户看到的打印结果。

实施验收必须从正式菜单、HTTP 路由和正常调度器进入，不能只直接调用新增函数。

### 6.2 发布不能自动制造“已确认”

当前 `reportPublishService.publishBatchReports` 在没有草稿时会生成默认评语并写 `CONFIRMED`，特定默认评语的陈旧草稿也会自动重建。这会让“管理员只发布”变成“发布时替老师确认”。新流程应取消这一兜底，要求已有真实的班主任确认；校验与发布对“已就绪”的定义必须一致。

### 6.3 自动汇总不等于自动臆测每格等级

取消终测导入后，必须定义“积分分类→过程评价”“学科能力→分项等级”“故事来源→读听讲”的映射。学校未确定阈值、权重、最终来源时，只能自动汇总已有正式值和提示缺项，不能凭总积分生成 74 格成绩。

同一荣誉或日常积分若已经参与分项/六维评价，不应再无条件沿用旧的综合分附加权重而重复计入。原 80/15/5 等历史结果按原版本保留；新规则需要学校确认后启用。

关联风险：当前 `commentProvider.generateCommentSuggestion` 是本地拼接文案，仍返回 `source: MODEL`、模型名和固定 token 数。它不是真实模型调用。本次如仅使用人工学期寄语，可以继续完成报告主链；如将“AI 生成初稿”纳入本期验收，需另行接入真实提供方并准确记录来源，不能把该占位服务当成已实现 AI。

| 健康 | 无业务路由 | 指定角色的预览、提交、本人/授权读取和状态接口 |
| 小程序结果 | 没有 | 最终成绩接收/确认/更正，认证来源、映射学生并幂等入库 |
| 发布 | 必须指定学生列表 | 只接收学校学期及准备版本，服务端生成全校名单；客户端不能改变发布范围 |
| 阅读和打印 | 分别拼装旧模型 | 统一读取已激活、已冻结快照，遵守同一权限和模板版本 |

## 8. 推荐实施顺序与验收

### 第一阶段：字段基线与权限

以已提供的测评明细图为起点，补齐正面和原 .doc，列出字段台账：合并字段名、报告位置、业务指标、视角、类型、来源、适用年级、必填规则。完成 74 项对账后冻结第一版字典。设计新增表与兼容迁移，先关闭新模式终测写入、修正学生指标读写权限。

阶段验收：一份逐字段台账可追溯到报告；类型/视角独立；历史报告不受影响；自评不能读写其他学生，任课教师不能修改其他学科正式值。

迁移采用增量方式：先加可空字段和新表、回填可确证的旧记录来源、部署新模式分流，再启用目标学期。旧指标有 `evaluated_by` 但不一定能证明是自评或他评，不能全部自动标成 SELF；不明来源保持历史标识并安排核对。已经使用的旧卡不改分类或班级，未用旧卡如需切换应先作废再按核定额度重新生成，并明确期初存量是否占新额度。上述切换政策须在上线前确认，但不应直接删除旧表。

### 第二阶段：卡片闭环

管理员下发 → 教师按多个班分配分类 → 校验总额/班额 → 一次生成 → 每班 PDF → ZIP → 学生扫码自动入账。

阶段验收：教师 100 张配额分给四班 20/25/25/30；一共只生成 100 个唯一卡，输出四份班级 PDF；任意分类、班级、学科明细均可对账。重复点击、并发生成、补打印不能多造卡；是否允许跨班领取按确认规则验收。

### 第三阶段：评价输入与来源

接通教师分项、自评、学期自述、健康数据、读听讲及外部成绩；钉钉手机登录在取得学校应用条件后并行接通。核心数据模型不能等到做报告时再补。

阶段验收：同一行为项保存自评二星、他评三星，互不覆盖；五个健康原始值和两个评价独立呈现；三项故事有各自评价和经历描述；月度正文和外部最终成绩互不覆盖；重复接收外部版本不重复计入。

### 第四阶段：核算、报告与全校发布

统一聚合服务，扩充草稿快照，按学校模板重做移动和打印视图，最后接全校发布任务。

阶段验收：

1. 不导入新学期六育终测分，也能从已批准来源生成六育结果；所需来源缺失时明确阻断，不回退旧终测表。
2. 报告快照含全部适用明细、双列、五方面自述、目标、三项故事描述、学期/家长寄语和开学月日。
3. 班主任确认后任一纳入报告的源数据改变，草稿失效；发布服务不能自动写成 CONFIRMED。
4. 正式菜单和 HTTP 入口覆盖完整流程；仅有服务级测试不算通过。
5. 手机竖屏按约定设备宽度验证，初步建议 375/390/430 CSS px；无关键信息截断和整页横向溢出。
6. 浏览器保存 PDF，核对 A4 正反两页、星级字形、表格双列、长文本和各项原始值；无 Word/Excel 报告导出需求。
7. 若采用统一可见方案，一名应评学生缺项时整批不激活；任务中断、重试、来源并发变化均不导致部分新报告对学生可见。
8. 重复发布同一请求不生成重复版本；新批次失败保留原已发布版本。管理员只看进度和缺项，不因新增自评/健康/打印接口获得个人正文访问权。

## 9. 待学校确认的业务决定

这些决定影响正式实施，不影响本次差异结论：

1. **原模板和字段台账**：已取得六板块测评图；补齐正面、原 .doc，并解释 74 与所列 68 项的差额；确认不同年级的适用项目。不能用设计稿的显示格数量代替 Word 合并字段数量。
2. **评价规则与来源**：积分怎样映射星级/六维；字母等级允许集合；是否仍计算总分；体测原值由谁提供；小程序提供总分还是读听讲分项，和校内评定谁为正式来源。
3. **全校一次性发布语义**：建议全校全部准备完成后一次可见；如允许跳过缺项学生，应明确例外名单和披露方式。
4. **班级卡归属**：只要求记录来源班级，还是同时禁止跨班领取；管理员额度的业务周期是否沿用当前月度。
5. **报告取舍与文本容量**：雷达图是否保留；学生自述、故事描述和寄语的 A4 两页容量规则，是否允许明确限制字数或使用附页。
6. **对接条件**：学校钉钉应用和身份目录、云美小故事最终结果样例及接收方式；不能以模拟回调代替真实登录。

### 11.2 图片对数据方案的补充

- 体质健康测试还有单独的“自我评价”空格，需在 `HEALTH_TEST` 对应指标配置中支持 SELF，不能只承载水平与过程两个教师值。

- 故事部分的“需分别评分”来自前文明确需求，图片仅有描述。页面保留图片的活动与文字列，并在中间增加评价列，三项分别保存。设计稿以星级字段预留，正式允许值和成绩来源仍按学校规则确认，未取得真实值前显示待评价。

### 11.3 排版和交互决定

这是本方案作出的设计选择：电脑以双栏呈现，左侧德美、智美，右侧健美、艺美、劳美、故事美；手机保持六板块顺序，智美按科目展开、艺美按音乐美术展开，逐项完整呈现而不缩成一张图片。空白示例统一显示“— / 待评价”，不推断成零分。所有示例都明确标注，暂不出现无数据来源的总分或雷达图。

页面包含六板块锚点、“标记待评价项”开关及浏览器打印按钮。此按钮使用浏览器保存 PDF，不新增服务端 Word/Excel 导出。测评明细的打印方向暂按附件比例采用 A4 横向单页；完整报告正反面的方向及最终双面排版仍应结合正面原稿确认。

本方案新增分析文档、无业务数据的结构清单和独立页面设计稿，没有改变正式产品代码、表结构、业务数据或生产配置。
